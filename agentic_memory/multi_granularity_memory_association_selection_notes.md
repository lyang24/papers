# MemGAS: Multi-Granularity Memory Association and Selection for Long-Term Conversational Agents

**Full title:** From Single to Multi-Granularity: Toward Long-Term Memory Association and Selection of Conversational Agents

**Authors:** Derong Xu, Yi Wen, Pengyue Jia, Yingyi Zhang, Wenlin Zhang, Yichao Wang, Huifeng Guo, Ruiming Tang, Xiangyu Zhao, Enhong Chen, Tong Xu (University of Science and Technology of China; City University of Hong Kong; Huawei Noah's Ark Lab)

**Paper:** arXiv:2505.19549v2 (v2 Sep 2025)

**GitHub:** https://github.com/quqxui/MemGAS

**Method name:** **MemGAS** (Memory **G**ranularity **A**ssociation and **S**election)

---

## The Core Problem

Retrieval-augmented memory systems let LLM conversational agents recall facts and preferences from past sessions despite limited context windows. But existing systems segment and retrieve memory at a **single granularity** — typically session-level chunks, or finer turn-level segments, or LLM-generated summaries. The authors argue this single-scale paradigm has two critical failure modes:

1. **Insufficient multi-granularity memory connection.** Systems that organize memory into topological structures (knowledge graphs like HippoRAG, trees like RAPTOR/MemTree) still concentrate on a single granularity (entities *or* session summaries). They fail to model cross-granular interactions between memory units, so a multi-session query may retrieve only *partial* useful information. The paper's motivating example: "How many online courses have I completed in total?" requires synthesizing "three courses on Coursera" (Conversation 1) with "two courses on edX" (Conversation 2) — answer "five." A single-granularity retriever that grabs only Conversation 1 returns the wrong answer ("three"). Establishing a link through a shared keyword/summary ("completed courses") is what enables full retrieval.

2. **Lack of adaptive multi-granular memory selection.** Methods rely on a *fixed* granularity strategy. But the best granularity is query-dependent: a coarse summary reduces noise but loses detail; a raw session retains detail but adds noise. The authors' empirical analysis (Figure 1a) shows that adaptively picking the *best-suited* granularity per query yields substantial gains — there is an inherent noise-vs-information trade-off that a fixed scheme cannot resolve.

## The Big Idea: Multi-Granularity Association + Adaptive Selection

MemGAS is a **training-free** framework built on two core strategies that mirror human-like memory consolidation:

1. **Memory Association** — Each session is expanded into a **multi-granularity memory unit** spanning four granularities, and a **Gaussian Mixture Model (GMM)** decides which historical memories to link to a new memory (accept set vs reject set), building a consolidated association graph.

2. **Granularity Selection** — An **entropy-based soft router** adaptively assigns retrieval weights to the four granularities per query, based on the certainty (Shannon entropy) of each granularity's query-relevance distribution. Retrieval then runs **Personalized PageRank (PPR)** over the association graph, and an **LLM-based filter** removes redundancy.

The four granularities for the i-th session `Si`:

| Granularity | Symbol | What it is |
|---|---|---|
| **Session-level** | `S` | The full raw conversation session |
| **Turn-level** | `T` | The session segmented into individual user/assistant turns |
| **Summary-level** | `U` | An LLM-generated session summary |
| **Keyword-level** | `K` | LLM-extracted keywords from the session |

Each memory chunk is `Mi = {Si, Ti, Ui, Ki}`, generated by `Ui, Ki = fLLM(Si)` and `Ti = segment(Si)`.

## Architecture

The framework has two phases (Figure 2): construction, then router-retrieval-filtering.

### Phase 1 — Multi-Granularity Association Construction

**Multi-granular metadata generation.** For each new session, an LLM agent generates the summary and keywords, and the session is segmented into turns. This produces the four-granularity memory unit stored in the memory bank `M`.

**Dynamical memory association (GMM).** When a new memory `Mnew` arrives:
- All memories are encoded to dense vectors with **Contriever**.
- Pairwise similarity scores are computed between `e(Mnew)` and every historical `e(Mj)`. Crucially, similarities are computed **granularity-specifically** — each granularity of `Mnew` is treated as a node and connects to nodes in the current bank.
- A **GMM** clusters the similarity vectors into two probabilistic sets:
  - **Accept Set** — high-similarity memories, which form direct associations (edges) with `Mnew`.
  - **Reject Set** — irrelevant memories, excluded from immediate connections.
- The association graph is updated incrementally: `Acur ← Acur ∪ Anew`, supporting real-time updates. This selectively reinforces contextually related memories, imitating human memory consolidation.

### Phase 2 — Multi-Granularity Router → Retrieval → Filter

**Entropy-driven granularity selection.** For query `q`, compute its similarity to all memory chunks at each granularity `g ∈ {session, turn, summary, keyword}`. Normalize the similarities to a probability distribution `pg` (softmax with temperature `λ`) and compute its **Shannon entropy** `Hg`. Low entropy = a sharp, confident match at that granularity; high entropy = ambiguous.

**Soft router weights.** Weights are the normalized *inverse* entropy:
```
wg = (1/Hg) / Σ_g' (1/Hg')
```
so granularities with higher certainty get larger weight — no manual tuning required.

**Memory retrieval (PPR).** The initial relevance score for memory node `Mi` is a router-weighted aggregation across granularities:
```
score_i = Σ_g wg · sim(q, Mi^g)
```
The top-α nodes seed a **Personalized PageRank** run over the association graph. PPR propagates relevance through graph structure, rewarding memories that are both directly query-relevant *and* densely connected to other high-value memories. After convergence, the top-K nodes become candidate context.

**LLM-based redundancy filtering.** The top-K memories plus the query are passed to an LLM with a designed prompt that discards irrelevant/repetitive content, yielding a concise, refined context for the final response `a = LLM(q, Mrel)`.

## Experimental Setup

- **Backbone LLM:** `gpt-4o-mini-2024-07-18` for both metadata generation and QA generation; temperature 0; zero-shot.
- **Encoder:** Contriever (used as retrieval backbone for all methods except Full History and MPNet).
- **Benchmarks (four long-term memory datasets):**

| LongMemEval-m | 500 | 501.9 | ~1,019,117 | User-AI |

- **Metrics:** GPT4o-as-Judge (4o-J), F1, BLEU-4, ROUGE-1/2/L, BERTScore, plus retrieval Recall@k and NDCG@k. Consistent top-3 session retrieval across models for fairness.
- **Baselines:** Full History (up to 128k tokens), MPNet, Contriever, MPC, RecurSum, SeCom, HippoRAG 2, RAPTOR, A-Mem.

## Single- vs Multi-Granularity (Table 5, LongMemEval-s)

This is the paper's central empirical justification — comparing each fixed granularity against the multi-granularity router.

| Granularity | 4o-J | F1 | BLEU-4 | R-1 | R-2 | R-L | BS |
|---|---|---|---|---|---|---|---|
| Session-level | 55.40 | 13.78 | 2.21 | 14.46 | 6.93 | 12.89 | 83.70 |
| Turn-level | 57.60 | 14.94 | 2.50 | 15.53 | 7.50 | 14.12 | 83.93 |
| Summary-level | 28.80 | 10.66 | 1.78 | 11.51 | 4.61 | 9.96 | 83.26 |
| Keyword-level | 17.20 | 9.05 | 1.61 | 9.82 | 3.61 | 8.20 | 82.84 |
| Naive Combination | 56.60 | 14.59 | 2.40 | 15.19 | 7.22 | 13.70 | 83.96 |
| **MemGAS (routed)** | **60.20** | **20.38** | **4.22** | **21.05** | **10.47** | **19.47** | **85.21** |

Key reading: no single granularity dominates (turn-level is best alone, summary/keyword alone are weak because they lose detail), and naively *concatenating* all granularities (14.59 F1) barely beats turn-level — it just adds noise. The **entropy-based router** is what unlocks the multi-granularity benefit, lifting F1 to 20.38. Granularity matters, but only *adaptive* granularity selection pays off.

| Variant | GPT4o-J | F1 | R@3 | R@5 | R@10 | QA Latency (s) |
|---|---|---|---|---|---|---|
| **MemGAS (full)** | **60.20** | **20.38** | **78.51** | **88.94** | **94.47** | 2.5534 |
| w/o GMM | 57.20 | 19.49 | 76.38 | 85.53 | 91.28 | 2.5506 (Δ0.0028) |
| w/o PPR | 56.60 | 19.76 | 75.96 | 85.96 | 90.64 | 2.5449 (Δ0.0085) |
| w/o MA | 56.80 | 17.69 | 74.89 | 85.74 | 91.49 | 2.5418 (Δ0.0116) |
| w/o Router | 56.60 | 18.88 | 75.53 | 85.74 | 92.34 | 2.5471 (Δ0.0063) |
| w/o All | 55.40 | 13.78 | 71.06 | 81.28 | 90.00 | 2.5343 (Δ0.0191) |

Findings:
1. Every component contributes — removing any one drops both QA and retrieval.
2. **w/o All collapses to a single-granularity baseline**: F1 falls 20.38 → 13.78 and Recall@3 falls 78.51 → 71.06, the steepest drop. The combination of association + selection is what carries the method.
3. **Memory Association (w/o MA)** is the single most damaging removal for F1 (→17.69), confirming the GMM-built association graph + PPR is the backbone.
4. The whole apparatus is cheap: the largest added latency is **0.0191 s** for QA and 0.0079 s for retrieval — a strong performance/efficiency balance.

## Key Takeaways

1. **Granularity is a first-class axis of memory design.** Rather than picking session vs turn vs summary, MemGAS materializes *all four* (session, turn, summary, keyword) per session and lets the query decide.

2. **Association before retrieval.** A GMM accept/reject clustering builds an explicit cross-granular association graph at write time, so multi-session answers can be assembled by traversing links (PPR) rather than hoping a single chunk contains everything.

3. **Entropy is an elegant, training-free selection signal.** Inverse-entropy soft weighting picks confident granularities per query with no learned router and negligible latency, directly addressing the noise-vs-information trade-off.

4. **Naive multi-granularity does not work** — concatenating all granularities barely beats the best single one (14.59 vs 14.94 F1). The win comes specifically from *adaptive selection* (20.38 F1).

5. **Strong gains at low cost.** Large F1/ROUGE improvements on four benchmarks (including a 1.5M-token-scale dataset) while keeping tokens and latency near lightweight retrievers and below graph baselines like HippoRAG 2.

---

## Limitations

1. **LLM-dependent metadata.** Summary and keyword granularities are LLM-generated; low-quality summaries/keywords (which already underperform alone — summary 28.8, keyword 17.2 on 4o-J) propagate into association and routing.
2. **Construction overhead.** Generating four granularities per session plus GMM clustering and graph maintenance adds write-time LLM cost vs flat vector stores (though query-time cost stays competitive).
3. **Tuning sensitivity.** Behavior depends on the entropy temperature `λ`, GMM clustering, and seed/Top-K choices (analyzed in appendices, but still hyperparameters).
4. **Conversational scope.** Evaluated only on text long-term dialogue QA/retrieval (LoCoMo, Long-MT-Bench+, LongMemEval-s/m); no multimodal or tool-using agent settings.
5. **Top-K noise.** Performance can degrade at large Top-K, leaning on the LLM filter as a backstop rather than fully solving the noise problem in retrieval itself.

## Where it sits (v1/v2)

**MemGAS is a v2 (2026-frontier-adjacent) multi-granularity memory association-and-selection approach.** It belongs to the second wave of agent-memory work that treats *how memory is structured and routed* as the central problem, not just *where it is stored*.

- **vs v1 flat / single-granularity stores (MemoryBank, MemGPT, A-Mem):** v1 systems keep a single representation level — MemoryBank stores summarized history with forgetting curves; MemGPT pages a flat hierarchy in and out of context like an OS; A-Mem builds Zettelkasten-style linked notes but retrieves by embedding similarity at one granularity. All commit to a fixed segmentation and retrieve by similarity/recency. MemGAS's contribution is precisely to break the single-granularity assumption: it co-indexes session/turn/summary/keyword and routes per query, beating A-Mem on every benchmark (e.g., LongMemEval-s F1 20.38 vs 13.73).

- **vs three-tier MemoryOS / MemOS:** MemoryOS introduces an OS-style tiering of memory (short / mid / long-term) — a *temporal/lifecycle* hierarchy of when memory lives where. MemGAS's hierarchy is orthogonal: a *granularity* hierarchy of how coarse each unit is, selected adaptively at retrieval time by entropy rather than promoted/evicted by lifecycle rules.

- **vs MAGMA's multi-graph routing:** MAGMA disentangles *relational dimensions* (temporal / causal / semantic / entity) into four orthogonal graphs and routes retrieval by query *intent* (WHY→causal, WHEN→temporal). MemGAS instead disentangles *granularity levels* and routes by per-granularity *entropy/confidence*. Both are v2 "route through the right structure" designs, but along different axes — MAGMA over relation type, MemGAS over abstraction level. They are complementary: one could imagine a system that is multi-graph *and* multi-granularity. MemGAS also leans on classical IR/graph machinery (GMM clustering, Personalized PageRank, Contriever, Shannon entropy) rather than MAGMA's neuroscience-inspired dual-stream write path, making it lighter-weight and fully training-free.

In short: where v1 asked "what do we store and when do we forget it," MemGAS asks **"at what granularity should we connect and recall each memory for this query"** — and answers it with GMM-built cross-granular associations plus an entropy router, the multi-granularity sibling of MAGMA's multi-relational routing.
